# Ponytail 在嵌入式编码中的适用性评估

## 结论

Ponytail 的核心思想适合用于嵌入式开发，但应当吸收为“解法选择与差异审查规则”，
不应原样作为嵌入式编码规范，也不建议当前直接以 `full` 或 `ultra` 模式全局常驻。

推荐采用的核心是：先确认需求真实存在，再依次复用现有实现、语言标准库、已验证的
BSP/SDK/RTOS 能力，最后才写最少且完整的代码。这里的“最少”指更少的概念、状态、
接口、依赖和维护面，不是最少行数，更不是把控制流压成一行。

Ponytail 与现有《嵌入式 C/C++ 编码规范》是互补关系：前者约束“是否需要写、选择哪种
解法”，后者约束“写出来的代码必须如何保证可读性、可移植性、并发与硬件安全”。

## 项目机制

Ponytail 是面向 AI 编码代理的规则和适配器集合，而不是 C/C++ 库。版本 4.9.0 的包将
核心行为放在 `skills/`，再由 Codex、Claude Code、OpenCode、Gemini 等宿主适配器加载。

其主要机制是七级阶梯：

1. 需求是否真的需要实现；推测性需求不实现。
2. 代码库是否已有可复用实现。
3. 标准库是否已经解决。
4. 平台原生能力是否已经覆盖。
5. 已安装依赖是否已经解决。
6. 是否能用一行表达。
7. 最后才编写能工作的最少代码。

规则还强调：先读完整调用链，再选择最小解法；Bug 应修在共同根因处；不得删除信任
边界校验、防止数据丢失的错误处理、安全措施和明确要求。`ponytail-review` 与
`ponytail-audit` 分别针对差异和整个仓库查找过度工程，但明确不负责正确性、安全和
性能审查。

## Deep module 视角

Ponytail 对“单实现接口、单产品工厂、无人修改的配置、纯转发 wrapper”的质疑是正确
的。它倾向减少没有提供 leverage 的 seam，使代码保持 locality。

但“删除接口”不应成为机械规则。嵌入式中的硬件抽象、协议边界、RTOS 适配、Bootloader
与应用边界，虽然有时只有一个当前实现，仍可能把大量寄存器、时序、字节序、错误恢复
和平台差异隐藏在一个小 Interface 后面。这类 Module 具有足够 Depth，应保留。判断标准
应是接口是否封装了稳定复杂度，而不是当前实现数量是否为一。

## 嵌入式适配

| Ponytail 原则 | 嵌入式解释 | 必要约束 |
| --- | --- | --- |
| 需求不存在则不写 | 不预留未确认的状态、命令、协议字段和兼容路径 | 已发布协议、诊断要求和安全机制不能按 YAGNI 删除 |
| 复用代码库现有实现 | 优先复用活动目标内已验证的模块与模式 | 相似目录或历史副本不算活动实现，必须由构建清单或调用链确认 |
| 标准库优先 | 优先使用工具链已支持、行为明确的 C/C++ 标准能力 | 先确认语言版本、实现质量、代码尺寸、异常与线程模型 |
| 平台原生优先 | 优先使用项目已验证的 BSP、HAL、SDK、RTOS 原语 | 不直接把供应商示例、未验证 API 或硬件理想模型当成可靠 contract |
| 已有依赖优先 | 避免重复引入同类库 | 仍要检查许可证、Flash/RAM、栈、WCET、可重入性和维护状态 |
| 一行优先 | 仅适用于真正简单、无副作用的表达式 | 业务分支、状态迁移、错误码、资源清理继续使用显式控制流 |
| 最小代码 | 减少状态、公共符号、层级、配置和依赖 | 不得删除边界检查、溢出检查、并发合同、硬件校准和失败恢复 |
| 最小可运行检查 | 每个非平凡改动留下定向验证 | 高风险代码不能只做一个 smoke test，必须服从项目构建和测试门 |

## 不应照搬的部分

1. **不能把 LOC 当质量目标。** 更短的三元表达式、复合布尔返回和宏可能比显式
   `if`/`else` 更难审计。
2. **不能机械删除单实现接口。** 硬件、协议、字节序、寄存器和 OS seam 可能是深模块
   的必要边界。
3. **不能把一个 smoke test 当作通用完成条件。** ISR、并发、协议、持久化、升级和
   安全相关改动需要与风险相称的静态分析、目标构建、测试或实机证据。
4. **不能先做最小 diff 再补理解。** 必须先确认活动构建目标、所有调用者、状态所有权、
   生命周期和硬件副作用。
5. **不建议全局启用 `ultra`。** 它主动挑战需求并优先删除，容易与项目规范、协议合同
   和安全要求冲突。
6. **暂不建议依赖插件常驻机制。** 项目适配面较广，但当前 issue 中仍有 review 模式
   持久化等活跃缺陷；复制并收紧少量规则更容易审计。

## 建议的嵌入式版阶梯

实现前按顺序判断，命中后停止继续增加复杂度：

1. 这是用户、需求、协议或缺陷证据确认的真实目标吗？未知则核验或询问，不猜。
2. 活动构建目标中是否已有正确实现或稳定模式？
3. 当前工具链支持的标准库是否能可靠解决？
4. 项目已验证的 BSP、SDK、RTOS 或硬件机制是否能解决？
5. 已有依赖是否在许可证、资源、时序、并发和生命周期约束内可用？
6. 能否减少一个状态、公共接口、依赖、配置项、文件或无语义 helper？
7. 最后才写满足完整 contract 的最小实现，并按风险完成验证。

“最小实现”必须同时保留：输入和长度边界、溢出检查、资源上限、错误处理、生命周期
对称、并发与 ISR 合同、协议/ABI、硬件校准、用户明确要求。

## 试点方案

先选择一个低风险、非 ISR、非安全关键、无公共 ABI 变化的局部任务，执行一次双重审查：

1. 正常完成根因分析、实现和项目规定验证。
2. 再做 Ponytail 式删除审查，只寻找多余依赖、单纯转发层、推测性配置、重复 helper、
   无活动调用者的兼容代码。
3. 记录修改前后新增行数、公共符号、helper、状态、依赖、Flash/RAM、编译告警和测试结果。
4. 只有在行为与资源证据不退化时，才接受更简单版本。

试点通过后，优先把“嵌入式版阶梯”和“删除审查”加入 Trellis `coding-rules`，不要直接
复制 Ponytail 的“一行优先”和 `ultra` 模式。

## 基准解读限制

项目自述的 agentic benchmark 在 12 个功能任务中报告平均新增 LOC 减少 54%，但主要
收益来自 Web 原生控件替代自建组件。实验只使用一个模型，每个单元 `n=4`，安全检查
只有 6 个小任务，且没有运行完整服务或浏览器。该结果支持“原生能力可减少过度实现”，
不能证明相同比例适用于嵌入式 C/C++，也不能替代目标构建、静态分析、资源测量和实机
验证。
