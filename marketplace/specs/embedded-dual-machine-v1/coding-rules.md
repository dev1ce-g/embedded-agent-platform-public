# 嵌入式 C/C++ 编码规范

本规范是嵌入式项目的强制编码基线，适用于新写代码和本次修改触及的
C/C++ 代码，并纳入代码评审中反复出现的可读性问题。汇编、生成代码、
第三方代码和供应商 SDK 按各自工具或上游规范处理。

## 1. 规则级别与优先级

- **必须**：不满足时不得声称代码质量检查完成。
- **应当**：默认遵守；偏离时必须有可核验的项目原因。
- **可以**：在不破坏上层规则时按项目需要选择。

发生冲突时，按以下顺序处理：

1. 安全要求、编译器或语言标准限制、公共 ABI、协议和生成器合同。
2. 最近作用域内明确写入 `AGENTS.md` 或 `.trellis/spec/` 的项目规则。
3. 本规范。
4. 当前文件和模块中未被规范覆盖的既有风格。

现有代码与本规范不一致时，只整理任务实际触及的代码。除非任务明确要求，
不得为统一格式而重写无关代码、公共名称或大段历史文件。

## 2. 修改前检查

修改 C/C++ 代码前，必须：

1. 读取最近作用域的 `AGENTS.md`、本规范和命中模块的其他 Spec。
2. 检查目标文件及同模块的 2-3 个代表性文件，确认命名、括号、布尔常量、
   生命周期、错误返回和注释风格。
3. 确认文件属于活动构建目标，而不是相似目录、历史副本或未引用实现。
4. 检查文件编码、换行符、生成来源和第三方边界。

完成条件：可以说明本次采用的项目风格、活动目标证据和允许修改的文件范围。

## 3. 文件、头文件与包含关系

- C 源文件使用 `.c`，头文件使用 `.h`，插入文本使用 `.inc`。
- 新文件名使用小写字母和下划线；现有公共文件不得仅为改名而调整。
- 每个头文件必须使用项目约定的 include guard。没有项目约定时，使用
  `_<PREFIX>_<FILE>_H_` 形式的大写标识符。
- 源文件首先包含对应头文件，然后依次包含 C/C++ 标准库、其他库和项目头文件。
- 包含顺序中的不同组之间可以使用一个空行。
- 不得新增以 `../` 或 `./` 开头的包含路径；应通过构建系统提供 include path。
- 预处理指令从行首开始，不缩进 `#`。

头文件必须自包含。公共头文件修改后，应当用项目支持的 C 标准和 C++ 标准分别
执行最小包含检查。

## 4. 作用域、初始化与所有权

- 局部变量放在满足可读性和工具链要求的最小作用域内，并在声明时初始化。
- 变量声明应集中在函数或逻辑子块开始处；不要在不相关语句之间穿插声明。
- 可变队列、ring、buffer 和状态默认由一个源文件或一个明确对象拥有。
- 默认使用文件内 `static` 限制内部全局对象的可见性。公共可变全局必须是明确的
  跨模块 ABI，并记录所有者、并发和生命周期合同。
- 静态存储期对象使用编译期可确定的初始化。不得依赖跨编译单元的构造、析构或
  有副作用初始化顺序。
- 初始化和销毁必须对称；部分初始化失败时，只释放已经取得的资源。

## 5. 类型、常量与可移植性

- 周边代码使用 `Bool`、`Byte`、`UInt8`、`UInt16`、`UInt32`、`Int32` 等项目
  类型时，新代码保持一致。
- 数值宽度、结构体布局、打印格式和指针转换必须同时考虑 32 位与 64 位目标。
- 整数零使用 `0`，浮点零使用 `0.0`，字符结束符使用 `'\0'`。
- C 指针使用 `NULL`；C++ 在工具链和项目允许时使用 `nullptr`。
- 优先使用 `sizeof(variable)` 或 `sizeof(*pointer)`，避免复制容易失配的类型名。
- 结构体、协议帧和共享内存布局必须显式处理对齐、字节序和大小校验。
- 变量和数组使用项目语言标准支持的初始化形式；C 代码默认使用 `=` 初始化。

## 6. 命名

- 名称必须表达领域含义。避免只靠大小写区分的名称，也不得让局部变量遮蔽同名
  全局变量。
- 文件、普通变量、参数和结构体成员默认使用小写加下划线。
- 常量默认使用 `kMixedCase`；宏使用大写字母和下划线。
- 函数沿用模块既有前缀和大小写风格；不得为了套用通用规则破坏公共 ABI。
- 可以使用项目内稳定、通用或领域公认的缩写。缩写必须在当前模块中可直接理解，
  不得删减到需要猜测，例如含义不清的 `nerr`、`cstmr` 或孤立的 `rc`。
- 名称过长并导致大量机械换行时，优先选择清晰的领域缩写或有语义的局部变量，
  不要逐参数展开来掩盖命名问题。
- 函数参数按输入、输入输出、输出的顺序排列；新增输入参数不得放在输出参数之后。

## 7. 表达式与控制流

### 7.1 三元表达式

新写或修改的代码默认使用显式 `if`/`else` 表达业务选择。以下场景不得使用三元
表达式：

- 控制流程、状态迁移或错误码选择；
- 直接 `return` 一个需要理解业务条件的三元表达式；
- 嵌套三元表达式；
- 任一分支包含函数调用、副作用或复合逻辑；
- 需要换行才能读懂的三元表达式。

只有同时满足以下条件时，才可以保留简单三元表达式：单一条件、两个分支均为
无副作用的简单值、完整表达式位于一行，并且比等价 `if`/`else` 更清晰。

```c
/* 可以：简单、无副作用、单行的值选择。 */
level = enabled ? kLevelOn : kLevelOff;

/* 应改为显式分支：状态和错误选择属于业务控制。 */
if (state == kStateReady)
{
    result = StartTransfer(self);
}
else
{
    result = kTransferBusy;
}
```

### 7.2 布尔表达式与返回

- 非布尔整数和指针参与条件判断时，使用与 `0` 或 `NULL` 的显式比较，除非项目
  已明确采用其他一致写法。
- 不要把多个具有独立失败含义的条件合并为难以定位原因的复合布尔直接返回。
  使用守卫分支或有业务含义的局部变量。
- `return` 简单表达式不加无意义括号。
- 条件内不得隐藏赋值、状态推进、资源取得或清理动作。

## 8. 行长度与断行

- 每行不超过 120 列。长 include 路径和 include guard 可以按项目规范例外处理。
- **120 列是上限，不是要求提前断行的目标。** 能在 120 列内清晰表达的短函数
  声明、函数调用、条件和完整业务表达式必须保持在一行。
- 不得仅因参数较多就在左括号后立即换行，也不得把每个参数机械拆成一行。
- 超过 120 列时，先检查名称是否冗长、表达式是否承担多个业务动作。可以通过清晰
  的领域缩写、局部变量或显式分支改善结构。
- 确实需要断行时，只在参数语义分组、布尔运算符或完整子表达式边界断开，并使用
  最少行数。续行缩进必须与当前项目一致。
- 同一声明、定义和调用采用相同的参数分组方式。

```c
/* 推荐：在行宽内保持完整。 */
Int32 DbSetCellVoltage(Db *self, Byte system_no, UInt32 cell_index, Word voltage);
return EnergyStorageSetVoltage(&self->energy_storage, system_no, cell_index, voltage);

/* 禁止：没有语义的逐参数断行。 */
Int32 DbSetCellVoltage(
    Db *self,
    Byte system_no,
    UInt32 cell_index,
    Word voltage);
```

长布尔表达式按运算符统一对齐：

```c
if (request_valid
    && session_ready
    && transfer_owner == kTransferOwnerLocal)
{
    StartTransfer(self);
}
```

## 9. 缩进、空格、括号与空行

- 只使用空格，每级缩进 4 个空格；不得添加制表符或行尾空白。
- 二元运算符两侧各留一个空格；一元 `!`、`~` 后不留空格。
- `(`、`)`、`[`、`]` 内侧不留空格；成员访问运算符前后不留空格。
- 指针声明中的 `*` 与变量名相邻，例如 `char *buffer`。现有模块有明确约定时保持
  模块一致。
- `{` 可以采用同一行或下一行风格，但一个文件和模块必须一致；不得在同一修改中
  混用两种风格。
- 条件、循环和 `switch` 即使只有一条语句，也应当沿用模块的大括号约定；新增代码
  优先使用大括号以降低后续修改风险。
- 以逻辑子块组织空行。局部变量、参数检查、主要逻辑和收尾之间通常使用一个空行；
  不得连续保留超过两个空行。

## 10. 函数结构与 `static` helper

函数通常按以下顺序组织：

1. 局部变量和必要的初始值。
2. 外部输入与真实前置条件检查。
3. 主要业务逻辑，按逻辑子块使用空行分隔。
4. 资源清理、状态提交和返回。

只验证调用边界上真实可能失效的输入。内部函数已经由类型、状态机或调用链保证的
不变量，不要重复加入无依据的防御性判断。

函数应当尽量控制在约 60 行以内。函数长度是复杂度检查信号，不是机械拆分命令。
新增 `static` helper 至少满足一项：

- 表达完整业务动作；
- 封装平台、SDK、硬件、协议、字节序或寄存器细节；
- 被两个或更多调用点复用；
- 拥有独立错误处理、清理、重试、状态迁移或回滚；
- 表达需要独立审计或稳定复用的领域不变量。

仅包装 1-2 个 API、只返回一个布尔表达式、只有 5-10 行且没有独立语义的 helper
应当内联。提取前必须确认：跳转到 helper 后，调用者是否比保留局部逻辑更容易读。

## 11. 宏与预处理

- 优先使用内联函数、枚举和常量；只有预处理能力确有必要时才新增宏。
- 宏参数和结果必须正确加括号，除非宏语义明确要求保留语法结构。
- 项目内部宏尽量靠近使用位置；短期局部宏使用后及时 `#undef`。
- 不得仅为复用名字而取消定义已有宏，也不建议使用 `##` 生成函数或变量名。
- 条件编译必须保持每条路径可构建；不得用宏隐藏无证据的兼容分支。

## 12. 注释与 Doxygen

- 公共 API 使用项目统一的 Doxygen 风格，写明功能、参数方向、返回语义、空指针
  规则、资源所有权、并发或重入前提以及重要性能限制。
- 文件头遵循项目模板。Git 已提供修改历史时，不在文件注释中维护重复且易过期的
  个人修改流水账，除非项目流程明确要求。
- 全局变量必须说明用途、所有者以及必须使用全局存储的原因。
- 实现注释解释非显然约束、硬件副作用、时序、协议兼容、并发顺序和设计原因；
  不复述代码表面动作。
- 单行使用 `//`，多行使用 `/* ... */`，并在同一文件中保持一致。
- TODO 必须包含可追踪的责任人、任务号或问题号；临时方案完成后删除 TODO。
- 注释使用完整、准确的中文或英文句子，保持标点、拼写和术语一致。

## 13. 嵌入式安全与并发

- 打包、解包和复制前必须验证目标容量、输入长度和算术溢出。
- MCU 热路径默认不引入动态分配，除非模块已经拥有明确的分配与失败模型。
- ISR、watchdog、HardFault 和 RTOS 错误路径必须最小、非阻塞；不得执行日志、
  动态分配、跨核发送或重型辅助逻辑。
- ISR 或近 ISR 生产、任务消费的 ring 是并发合同：先写 payload，再发布写索引；
  消费者先读 payload，再推进读索引。
- `volatile` 不能单独证明原子性或内存顺序。原子性不明确时，使用短临界区或项目
  已验证的 IRQ-safe 原语，并记录单生产者/单消费者等前提。
- 初始化、运行、停止和销毁路径必须保持状态与资源对称。

## 14. 生成代码、第三方代码与编码

- 不直接修改生成文件；修改生成源并重新生成，或记录受控例外。
- 不直接修改第三方库和供应商 SDK，除非任务明确授权并有补丁维护策略。
- 保持现有文件编码和换行符。旧文件包含非 UTF-8 注释时，不得为统一编码而整文件
  重写；新文件默认使用 UTF-8。
- 不得在行尾添加空白。

## 15. 质量检查

完成 C/C++ 修改前，必须对本次差异执行以下检查：

1. 逐个审阅修改过的声明、调用、条件和返回表达式，确认没有机械逐参数换行、
   费解三元表达式、条件内赋值或无意义 helper。
2. 检查行宽、制表符、行尾空白、连续空行和括号风格。
3. 运行 `git diff --check` 或等价检查。
4. 运行项目规定的格式、静态分析、目标编译和测试；只声明实际执行并通过的层级。
5. 检查头文件自包含、声明与定义一致、32/64 位相关格式和结构体大小假设。
6. 确认未格式化无关代码，未改变生成文件、第三方代码或旧文件编码。

自动检查只能发现候选问题。行宽通过、格式化工具通过或退出码为零，均不能代替
对业务分组、命名、控制流和可读性的人工差异审查。

## 16. 规则覆盖

| 主题 | 本规范覆盖 |
| --- | --- |
| 头文件与包含 | 自包含和双语言包含检查 |
| 作用域与初始化 | 所有权、生命周期和失败清理 |
| 函数与参数 | 约 60 行作为检查信号，限制低价值 helper |
| 类型、宏与可移植性 | ABI、协议布局和溢出检查 |
| 命名 | 允许清晰领域缩写，禁止因冗长名称制造机械换行 |
| 注释 | 公共 API Doxygen 和所有权合同 |
| 格式与留白 | 最小断行、三元表达式和差异质量门 |
| ISR 与并发 | 嵌入式运行时安全扩展 |
